# Design Brief: Sui の UI/UX 見直し（ポップ化）

## 目的と成功指標
- **解く課題**: 今の UI は「地味・ありきたり」（グレー＋青緑、端末の標準フォント）で、触りたくなる感じがない。さらに「次に何をすればいいか」が全体的に弱く、ホームの「診断」と「条件えらび」の違いも分かりにくい。
- **ねらい**: 友達に見せたくなる、ポップで遊び心のある見た目にする。どの画面でも次に押すものが1つに分かる流れにする。
- **成功の目安**:
  - ホームを開いて迷わず診断を始められる
  - どの画面でも「主役のボタン」が1つに決まっている
  - 実機（iPhone / Expo Go）で触って、ユーザーが「いい感じ」と判断する
  - （プロダクトの指標）決定率・「行った」率・2回目の利用は `analytics.summary` で見る

## 対象ユーザーと利用状況
- 沖縄本島中部の大学生・専門学校生
- 友達と集まる前後に、スマホ（主に iPhone、Expo Go / Web）で使う。友達はリンクから Web 版で投票に参加することが多い
- 片手でタップ中心。集まって画面を見せ合うこともある

## スコープ
**やること（見た目＋主な流れ）**
- 色・文字・部品（ボタン、選択肢、カード、シート、状態表示）を新しいデザインに作り直す
- ホーム：診断を主役に。条件えらびは「自分で条件を決める」の小さなリンクに下げる
- 診断（/quiz）・結果（/quiz/result）・候補（/picks）・条件えらび（/new）・投票（/o/[code]）・決定画面を新デザインにそろえる
- どの画面も、主役のボタンを1つにする（ほかは控えめに）

**やらないこと**
- 画面の数や機能の追加（ドライブコース、スタンプなどは別の作業）
- ダークモード（明るい表示に固定のまま）
- DB・API の変更

## 画面と状態
- ホーム（初めて / 参加したおでかけあり）
- 診断 5問（場所・お腹・気分・外か中か・お財布）、結果（タイプ＋候補3つ）
- 条件えらび、候補3つ
- 投票（参加前の名前入力 / 投票中 / 作成者の「ここに決定！」）、決定画面（＋「実際に行った？」）
- 共通の状態：読み込み中、エラー、見つからない、オフライン、CAPTCHA

## 制約
- Expo SDK 58 + Expo Router + NativeWind v4（Tailwind v3）、React Native 0.88、Web 版あり（EAS Hosting）
- Reanimated の `Animated.View` には NativeWind の className が効かない（style で書く）
- 自作の Reanimated `Keyframe` は Web で表示されないことがあった（組み込みの FadeIn 系を使う）
- iOS 26 の半透明ヘッダー（ScrollView は `contentInsetAdjustmentBehavior="automatic"`）
- 開発に使う Mac はメモリ 8GB。シミュレーターは使わない（実機で確認してもらう）
- a11y：WCAG AA のコントラスト、タップ領域 44pt 以上、読み上げのラベル、視差効果を減らす設定への対応
- アニメーションは expo-animation スキルの方針（ease-out、UI は 300ms 以内、押した瞬間の反応）

## トーン・参考
- **雰囲気**: ポップで遊び心。診断アプリやゲームのように、色がはっきりしていて、動きも楽しい
- **色**: 沖縄の**海の青**をメイン、大事なボタンは**夕日のオレンジ**、背景は**温かいクリーム色**
- **文字**: 丸いフォント（M PLUS Rounded 1c など）。読み込みが少し重くなるのは許容
- 手書きの「Sui」ロゴ（アイコン）はそのまま使う。アイコンの色（青緑）はブランド色との兼ね合いで、必要なら次の作業で見直す

## 完了条件
- ホーム・診断・結果・候補・条件えらび・投票・決定の画面が、新しい色・文字・部品にそろっている
- どの画面でも「次に押すもの」が1つに分かる
- 型チェック・lint が通り、Web でスマホ幅の表示を確認済み
- ユーザーが実機で確かめて OK

## 未解決事項
- アプリのアイコン・スプラッシュの色を、新しいブランド色に合わせるか（今回は据え置き）
- スポットの写真がほとんどないので、写真の代わりの見せ方（カテゴリの色とアイコン）をどこまで華やかにするか → ステップ3で提案

## UX 戦略

### ユーザーと利用状況
1. **言い出しっぺ（作る人）**：大学生・専門学校生。友達と遊ぶ当日〜数日前、LINE で「どこ行く？」が止まったときに開く。iPhone のアプリ（今は Expo Go）か Web。片手、数分以内に決めたい。月に数回（推測）。
2. **参加者（投票する友達）**：LINE で届いたリンクから、ほぼ Web（LINE のアプリ内ブラウザが多いと推測）で開く。アプリは入っていない。1回きりで、10秒で投票して戻りたい。

### Jobs to be done
- 友達と遊ぶとき、行き先がなかなか決まらないので、**数タップで「ちょうどいい3つ」を出して、そのまま友達に聞きたい**。毎回同じ場所になるのも避けたい。
- 友達からリンクが届いたとき、**アプリを入れずにすぐ投票したい**。面倒なら参加しない。
- 行き先が決まったら、**すぐ地図で向かいたい**。

### タスク優先度
- **一次**：言い出しっぺが「診断 → 3候補 → 友達に送る」を終える
- **二次**：参加者が投票する／作った人が決定する／決まった場所を地図で開く
- **三次**：自分で条件を決める（/new）、引き直し、診断結果のシェア、参加したおでかけの一覧、「実際に行った？」

### 主要フロー
**一次（言い出しっぺ）** 合計 9〜10 タップ
1. ホーム：「診断スタート」をタップ（判断なし）
2. 診断 5問：1問1タップ（場所だけ「市町村からえらぶ」で＋1）。天気の取得は裏で待つので待ち時間なし
3. 結果：タイプの発表 → 3候補（候補の取得 0.5〜1秒）。判断：「この3つでいいか」→ だめなら「引き直す」
4. 「この3つで友達に聞く」→（初回だけ CAPTCHA、自動で通ることが多い）→ 名前（2回目からは入力済みで1タップ）
5. 投票ページ ＋ 共有シート（アプリ）／コピー（Web）→ LINE に貼る
6. みんなの投票を待つ（Realtime で反映）→「ここに決定！」→ 決定画面 → Googleマップ
- **削れるもの**：名前の入力（2回目以降は確認だけ）。共有は自動で開く（アプリ）。

**二次（参加者）** 合計 3 タップ
1. LINE のリンク → 投票ページ（初回は CAPTCHA）→ 名前 → 「参加する」
2. カードをタップで投票 → 「決まるのを待ってね」
3. 決定されると画面が切り替わる → Googleマップ

### つまずきポイントと対処
| 場面 | つまずき | 対処 |
|---|---|---|
| ホーム | 「診断」と「条件えらび」の違いが分からない | 主役は診断の1つだけ。条件えらびは「自分で条件を決める」の小さなリンク |
| 初回 | 何のアプリか分からない | ホームに3行の使い方（今のまま）。診断カードに「5問・30秒」と所要を書く |
| 作成直後 | 投票ページで、次に何をするか分からない（送る？待つ？決める？） | ページの上に**進み具合**（①友達に送る ②投票を待つ ③決定）を出し、主役のボタンを状態で切り替える：他の人の票がまだ → 「友達に送る」、票が集まった → 「ここに決定！」 |
| 投票後（参加者） | 投票したあと、何を待てばいいか分からない | 「投票したよ。決まったらこの画面が切り替わるよ」と明示 |
| 候補が少ない | 「条件ゆるめ」の意味が分からない | 結果の上に一文で説明（今のまま）、候補ゼロなら「エリアを変える」を主役に |
| 中断 | アプリを閉じて戻ったら、どこにいたか分からない | ホームの一覧で「投票中」を上に。作った人には「決定待ち」の印 |
| 取り消し | 投票を間違えた | 別のカードをタップで変更できる（今のまま）。決定は確認シートで一度止める |
| エラー | 通信・位置情報・天気 | 今の共通部品（Problem / オフラインの帯）を新デザインに。位置情報がだめなら市町村へ誘導 |
| Web（LINE内） | 共有シートがない | コピー＋「LINEに貼ってね」（今のまま） |

### 画面ごとの情報階層
- **ホーム**：①診断スタートの大きなカード（タイトル＋「5問・30秒」）→ ②投票中のおでかけ（あれば）→ ③「自分で条件を決める」リンク・使い方・規約
- **診断**：①質問文（大きく）→ ②選択肢カード（大きく、絵文字つき）→ ③進み具合・戻る（控えめ）
- **結果**：①タイプ（小さめのカードで、3候補のうち1枚目が最初の画面に見える高さに収める）→ ②3候補 → ③主役「この3つで友達に聞く」、控えめ「引き直す」、さらに控えめ「シェア」「もう一回」
- **候補（/picks）**：結果と同じ（タイプなし）
- **条件えらび（/new）**：①場所 → ②気分・予算・車 → ③天気（自動）→ 主役「3つ出す」
- **投票**：①進み具合と「今すること」→ ②3候補（自分の票・票数・名前）→ ③主役ボタン（状態で切り替え）
- **決定**：①決まった場所（大きく）→ ②主役「Googleマップで開く」→ ③（3時間後）「実際に行った？」→ 誰が投票したか

### UX 上のリスクと未検証の仮説
- **仮説**：迷っている人は「条件」より「診断」のほうが早く決められる → 診断経由のおでかけ作成率で確かめる（`conditions.quizType` で区別できる）
- **リスク**：ポップにしすぎると、票数や名前などの情報が読みにくくなる → 本文は落ち着いた色、色の強さは主役のボタンとタイプのカードに集中
- **リスク**：丸いフォント（日本語）はファイルが大きく、Web の初回表示が遅くなる → 太さは2種類まで。Web は Google Fonts（必要な文字だけ読み込む）を検討
- **リスク**：LINE のアプリ内ブラウザでの見え方・CAPTCHA の動き → 実機の LINE から開いて確認する
- **未検証**：作った人が自分も投票するか（今は作った人も投票できる）
